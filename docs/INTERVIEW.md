# 面试问答准备(ReflexRAG)

按追问深度分层准备:★ 基本盘 / ★★ 深挖 / ★★★ 高手过招。

## 一、架构与决策

**★ 为什么不用 LangChain/LlamaIndex?**
框架-free 实现:agent 循环(路由/迭代/校验)每一步都要自定义,
框架抽象反而碍事;自己写才能在面试中讲清每个细节。代价是轮子多,
但本项目规模(~2.5k 行)可控。也说明:不是不会用框架,是框架解决不了
我的核心需求(自适应路由 + 充分性循环)。

**★ RAG 的完整链路?**
摄取(抓取→frontmatter 解析→结构感知分块→嵌入→Qdrant + BM25 双索引)
→ 查询(分析路由→规范化/分解→混合检索→RRF 融合→可选 rerank)
→ 生成(证据编号注入→流式生成→引用提取)
→ 校验(越界代码拦截→忠实性 LLM 审查→必要时重生成)。

**★★ 为什么 RRF 不用分数加权融合?** → 见 docs/DESIGN.md #2,带实测数据。

**★★ 多轮对话怎么做的?**
分析器接收最近 4 轮对话,提示词里明确"仅供消解指代,不要回答历史问题",
把"那试用期呢"还原成独立完整问题再路由,避免污染检索。

**★★★ 如果 QPS 上来怎么办?**
分层:LLM 调用是瓶颈→分析器/裁判用小模型 + 语义缓存(相似问题命中直返);
检索→Qdrant 服务端模式 + 读写分离;嵌入→批量 + 本地缓存;
再往上→预计算高频问题的答案索引。

## 二、检索与分块

**★ chunk 大小怎么定的?**
不是拍脑袋的 512:法条是天然原子单元,按条文边界切、~520 字目标合并,
实测平均 363 字。关键不是数字而是"结构感知"——知道什么是不可分割单元。

**★★ 召回率上不去怎么办?**
先看 bad case 分类:字面查询漏→BM25 补;语义改述漏→换更强 embedding/
查询扩展;多跳漏→子查询分解(本项目方案);排序错→rerank。
不同病因不同药,所以评测集要先按错误类型归因。

**★★★ 你的多跳证据召回为什么反而降了?**(必被追问,主动讲)
多个子查询分摊 top-8 名额,稀释了原始查询的命中。改进:多跳时动态
提高 final_top_k、或对原始查询命中的块 RRF 加权。这也是我下一步的
调优实验——体现"评测驱动迭代"的工作方式。

## 三、评测(最大差异化点)

**★ 怎么证明你的系统比朴素 RAG 好?**
73 题金标集(单跳29/多跳22/闲聊10/超范围12),三配置消融:
路由准确率 27%→75%、拒答 100%、忠实性 2.62→3.45、p50 延迟反降。
每个数字可复跑(scripts/run_eval.py)。

**★★ 金标集怎么建的?会不会有偏?**
种子题(闲聊/超范围人工写)+ 法条反向出题(LLM 从条文生成问题和金标答案,
金标证据=该条文块,天然精确)。偏差:LLM 出题的语言风格与真实用户有差;
缓解:出题提示词强制口语化,且人工抽检。固定随机种子可复现。

**★★ LLM-as-judge 可信吗?**
忠实性(证据是否支持陈述)裁判较可靠,因为它只做核对;正确性(与金标
对比)受裁判模型能力上限影响,qwen3.7-flash 偏严、方差大——这正是
"正确性只提升 0.19"的部分原因,改进方向是强裁判模型或投票。
敢讲裁判的局限反而加分。

**★★★ 为什么用小模型做裁判不怕偏见?**
裁判与被测系统同模型会有自我偏好,但本项目裁判只看(问题/金标/证据/回答)
四方对照,不涉及风格偏好;且三配置用同一裁判,对比是公平的。
绝对分数可能有偏,相对结论稳健。

## 四、工程与坑(真实经历即加分)

**★ 遇过最难的 bug?**
三个都有得讲:①本地 Qdrant 独占文件锁,Web 服务运行时评测进程起不来
→评测用只读快照解耦,Docker 模式上 Qdrant 服务端根治;②思考型模型
(qwen3.8-flash)每题烧 ~3000 思维链 token,免费额度两次跑干→
extra_body 透传 enable_thinking=false,成本降约 10 倍;③修正重生成的
答案会追加到 SSE 流,前端显示两份答案→reset 事件清空再收流。

**★★ 流式输出的 token 怎么统计?**
stream_options.include_usage 从流尾帧拿真实用量;供应商不回传时
按字符数估算兜底。成本统计从"约估"变成"实报"。

**★★ 断点续跑怎么做的?**
评测按配置落盘 per_item.json 检查点,单题异常标记 error 不炸整轮,
聚合时错误样本单独统计错误率、不混入均值。

**★★★ 部署架构?**
docker-compose:Qdrant 服务端(数据卷持久化)+ API 容器(env 注入,
QDRANT_URL 切服务端模式);首次启动容器内跑 ingest 建索引。
CI:GitHub Actions,ruff + pytest + 导入冒烟。

## 五、发散题

**★★★ 给你 10 倍数据(130 部法规)什么会先坏?**
分析器提示词里的语料清单会爆→改成向量检索"已知法规域"再注入;
BM25 索引内存线性增长→考虑分片或换服务端;评测集要按法规分层扩充。

**★★★ 这个项目离产品还差什么?**
责任边界(法律免责声明已有但需更正式)、时效性(法规修订的增量更新
管道)、地方性法规冲突处理、专业律师评审回路、更严格的正确性验收线
(法律场景错误成本高,3/5 的正确性远不够)。
